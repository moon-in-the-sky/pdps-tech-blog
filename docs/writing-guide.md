# 선택 근거 중심의 글 작성 원칙

## 목적과 문체

플랫폼을 개발한 배경, 제공하는 서비스의 이유, 구조와 기술을 선택한 판단, 검증 결과를 기록한다. 동시에 코드에 연결되는 이론을 개념마다 한 편씩 깊게 공부한다.

사용자가 수정한 1편의 문체를 기준으로 한다. 업무와 동작을 구체적으로 설명하고, 과장된 성과나 추상적인 수식어로 분량을 늘리지 않는다. 이론의 정의만 설명하지 않고 해당 플랫폼의 문제로 시작한다.

## 공통 전개

1. 해결해야 하는 문제: 실제 업무나 구현에서 무엇이 어려웠는가?
2. 요구사항과 제약: 정확성·속도·메모리·운영 환경 중 무엇을 만족해야 하는가?
3. 가능한 선택지: 어떤 방법들이 문제를 해결할 수 있는가?
4. 비교 기준: 장점·비용·실패 조건을 같은 기준으로 비교한다.
5. 선택한 방법과 구현: 선택의 근거와 코드 적용 위치를 연결한다.
6. 검증과 한계: 기대 효과와 관측 결과를 구분하고 포기한 조건을 설명한다.
7. 선택을 바꿀 조건: 규모나 요구가 달라졌을 때 필요한 대안을 설명한다.

## 사실의 구분

- 당시 선택: 실제 당시 고려한 내용. 코드만으로 최초 선택 이유를 확정하지 않는다.
- 사후 검증: 구현 후 실험이나 운영에서 확인한 결과.
- 추가 비교: 원고 작성 과정에서 조사하거나 실험한 대안.
- 확장 학습: 현재 적용했다고 확인하지 않은 개념의 원리·대안 실험.

비교하지 않았던 후보를 당시 검토한 것처럼 작성하지 않는다. Python에 익숙했다는 식의 개인적 이유도 사용자 확인이나 당시 기록 없이 만들어 넣지 않는다.

## 개발 글

서비스가 필요한 이유 → 요구사항·환경 제약 → 구조·대안 비교 → 구현 흐름 → 검증 결과 → 남은 문제 순서로 작성한다. 관련 이론 글을 연결한다. 모든 이론을 개발 글 안에서 다시 길게 설명하지 않는다.

## 이론 글

플랫폼의 구체적인 문제 → 정의·원리·전제 → 작은 예제 → 프로젝트 코드의 적용 위치 → 대안 비교 실험 → 한계·선택 조건 순서로 작성한다.

학습 완료 기준은 정의 설명, 코드 추적, 실험 재현, 실패 조건 설명을 모두 할 수 있는가이다. 효과가 없었던 실험도 기록한다. 개념에 따라 속도 대신 정확성·자원 사용·유지보수성을 검증할 수 있다.

## 제목 예시

| 개념 | 문제와 판단을 드러내는 제목 |
| --- | --- |
| 해시 테이블 | 패킷마다 파라미터 정의를 어떻게 찾을까 — 순차 탐색과 해시 인덱스 비교 |
| 위상 정렬 | 등록 순서대로 계산해도 될까 — 의존성에 따라 실행 순서 정하기 |
| LRU | 출력 파일을 모두 열어둘 수 없다면 — 파일 핸들 관리 방식 비교 |
| 커넥션 풀 | 동시 요청에서 DB 연결이 부족해졌을 때 — 연결 수와 점유 시간 검토 |
| 세마포어 | 다운로드 병렬 작업을 얼마나 허용할까 — 처리량과 자원 사용의 균형 |
| 메모리 매핑 | 대용량 원본 파일을 어떻게 읽을까 — 일반 읽기와 메모리 매핑 비교 |

모든 개념에 선택 서사를 억지로 붙이지 않는다. 2의 보수나 엔디언은 규격에 맞는 해석이 핵심이므로, 대안의 선택보다 해석 오류와 정확성 조건을 중심으로 쓸 수 있다.

## 플랫폼 설명의 기준

- 원시 파일을 먼저 처리하고 FPB2 결과를 저장한 뒤 사용자 요청에 맞춰 추출한다. 요청마다 원시 파일을 처리하는 on-demand 구조로 설명하지 않는다.
- 값뿐 아니라 시간·샘플 수·누락·중복을 정확성 기준에 포함한다.
- 누락을 임의로 0으로 채우거나 비정상으로 보이는 시간 구간을 근거 없이 제거하지 않는다.
- 개별 Raw 다운로드와 여러 파라미터의 시간축 정렬 정책을 구분한다.
- 시간 정렬 정책과 현재 코드는 원고 작성 시 재확인한다. 의도한 정책과 구현 완료 상태를 혼동하지 않는다.
- 서비스 제공 이유를 해당 개발 글의 도입에 포함한다. 별도 서비스 소개 글을 다시 만들 필요는 없다.

## 성능·검증 기록

측정에는 코드 커밋, 입력 파일 크기와 파라미터·행 수, 서버 사양, 저장장치, 네트워크, 워커 수, 동시 요청 수, 출력 형식, 압축 수준, 캐시 조건, 반복 횟수를 함께 기록한다.

측정값, 계산한 예상값, 확인하지 않은 가설은 구분한다. 기존 결과와 같다는 것만으로 정확성을 확정하지 않는다. 모델 선언 확인과 운영 DB의 실제 제약 확인도 구분한다.
