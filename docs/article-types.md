# 글 유형별 전개 양식

기술 블로그 글은 독자가 던지는 질문에 따라 전개가 달라진다. 이 문서는 유형별 전개 양식과 주의점을 기록하고, 이 연재(연재 개발기)에서 유형을 어떻게 쓰는지 정한다. 유형의 분류는 일반적인 글쓰기 관행을 정리한 것이며 특정 자료의 조사 결과가 아니다.

## 이 연재에서의 사용 원칙

- 큰 틀은 **연재 개발기**다. 배경 → 기술 선택 → 기능 개발 → 검증 → 운영 순서로 이어지며, 편 사이의 연결과 순서는 `series-plan.md`가 정한다.
- 개별 글과 절의 세부 전개는 아래 **유형**에 따라 나눈다.
- 한 글에는 **주도 유형을 하나** 두고, 다른 유형은 일부 절로만 섞는다. 예를 들어 기술 선택 글 안의 개념 설명은 결정 근거에 필요한 만큼만 쓰고, 깊은 설명은 별도의 개념 설명 글로 연결한다.
- 글 상단의 메타 주석에 `<!-- 유형: 주도 유형 (+ 부분 유형) -->`을 적는다.
- 사실 구분(당시 선택, 사후 검증, 추가 비교, 확장 학습)은 모든 유형에 적용한다. 자세한 규칙은 `writing-guide.md`를 따른다.

## 유형을 고르는 기준

| 독자가 하는 일 | 중심 | 해당 유형 | 핵심 요소 |
| --- | --- | --- | --- |
| 그대로 따라 한다 | 재현 | 튜토리얼, 트러블슈팅 | 환경, 버전, 명령 |
| 원리를 이해한다 | 이해 | 개념 설명 | 손으로 추적할 수 있는 예제 |
| 근거를 보고 자기 상황에 대입한다 | 판단 | 기술 선택, 설계, 도구 비교 | 요구사항, 비교 기준, 한계 |
| 결과를 믿어도 되는지 확인한다 | 증명 | 성능 실험 | 측정 조건, 원본 기록 |
| 경험에서 교훈을 얻는다 | 회고 | 프로젝트 회고 | 과정과 판단, 아쉬운 점 |

## 1. 기술 선택 (의사결정 기록)

- 독자의 질문: 왜 이 도구·방법을 골랐는가?
- 전개: 배경과 해결할 문제 → 요구사항과 제약 → 선택지 → 비교 기준 → 선택과 적용 → 결과와 한계 → 선택을 바꿀 조건
- 필수 요소: 당시 실제로 고려한 후보와 이유, 비교의 시점 표시(당시 선택 / 사후 검증 / 추가 비교), 선택을 바꿀 조건
- 주의: 선택한 뒤에 후보와 이유를 소급해서 만들지 않는다. 당시 기록이나 사용자 확인이 없으면 `[확인 필요]`로 남긴다. 코드와 문서에 이유가 적혀 있어도 최초 동기로 단정하지 않는다.
- 이 연재: 02-1(React), 3편(FastAPI), 4편(PostgreSQL)

## 2. 설계·아키텍처

- 독자의 질문: 전체가 어떻게 구성되어 있고 왜 이렇게 나누었는가?
- 전개: 목표와 비목표 → 구조(그림이나 표) → 데이터와 제어의 흐름 → 트레이드오프 → 버린 대안 → 알려진 한계
- 필수 요소: 그림과 설명의 일치, 구성 요소별 책임, 실제 코드 경로
- 주의: 구조 소개로 끝내지 않고 "왜 이 경계로 나누었는지"를 쓴다. 설계안과 구현 완료 상태를 구분한다(예: 구현하지 않은 배포 설계안은 "설계한 방향"으로 쓴다).
- 이 연재: 02-2(함께 쓰는 도구), 5편, 10편, 34편, 45편, 50편, 56편

## 3. 개념 설명 (이론·학습 글)

- 독자의 질문: 이것이 무엇이고 어떻게 동작하는가?
- 전개: 플랫폼의 구체적인 문제 → 정의·원리·전제 → 작은 예제 → 프로젝트 코드의 적용 위치 → 대안 비교 실험 → 한계와 선택 조건
- 필수 요소: 정의 직후의 작은 예제, 코드 추적, 실패 조건
- 주의: 정의만 나열하지 않는다. 적용했다고 확인하지 않은 개념은 "확장 학습"으로 표기한다. 근거 없는 일반화(예: 검증하지 않은 성능 주장)를 쓰지 않는다.
- 학습 완료 기준: 정의 설명, 코드 추적, 실험 재현, 실패 조건 설명을 모두 할 수 있는가
- 이 연재: 이론 글 전체(선언형·명령형, state와 props, 상태의 분류, 단방향·양방향 포함)

## 4. 성능 개선·실험 보고

- 독자의 질문: 정말 좋아졌는가? 어떤 조건에서인가?
- 전개: 문제와 지표 → 측정 환경 → 가설 → 변경 → 전후 결과 → 효과가 없었던 시도 → 한계
- 필수 요소: 코드 커밋, 입력 규모, 서버 사양, 저장장치, 네트워크, 워커 수, 동시 요청 수, 출력 형식, 캐시 조건, 반복 횟수
- 주의: 측정값, 계산한 예상값, 확인하지 않은 가설을 구분한다. 효과가 없었던 실험도 기록한다. 정적 코드 구조를 성능의 근거로 쓰지 않는다.
- 이 연재: 64편, 65~67편

## 5. 트러블슈팅 (문제 해결 기록)

- 독자의 질문: 이 증상은 왜 생겼고 어떻게 해결했는가?
- 전개: 증상 → 환경과 재현 조건 → 원인 추적 과정 → 해결 → 재발 방지
- 필수 요소: 증상을 보여주는 로그나 화면, 원인에 도달한 과정, 해결 전후의 확인
- 주의: 해결책만 쓰지 않고 원인을 어떻게 좁혔는지 쓴다. 원인을 확정하지 못했다면 가설로 표기한다.
- 이 연재: 별도 편은 없고 개발 글 안의 사례(예: 오래된 응답이 최신 화면을 덮어쓰는 문제)로 쓴다.

## 6. 튜토리얼 (따라 하기)

- 독자의 질문: 어떻게 만들거나 설정하는가?
- 전개: 목표와 결과물 → 준비물과 환경 → 단계별 진행 → 결과 확인 → 막혔을 때
- 필수 요소: 버전과 환경, 복사해서 실행할 수 있는 명령, 각 단계의 기대 결과
- 주의: 직접 실행해서 확인한 단계만 쓴다. 실행하지 않은 절차는 계획으로 표기한다.
- 이 연재: 72편(폐쇄망 배포·운영 절차)에서 구현 후 일부 사용. 현재 배포 스크립트는 설계안이므로 지금은 적용하지 않는다.

## 7. 도구·방법 비교

- 독자의 질문: 어떤 상황에서 무엇을 써야 하는가?
- 전개: 비교 기준 → 항목별 비교 → 상황별 선택 조건
- 필수 요소: 같은 기준으로 비교한 표, 비교의 시점 표시
- 주의: 직접 써 보지 않았거나 확인하지 않은 특징은 "일반적으로 알려진 특징"으로 쓴다. 공식 문서를 근거로 쓸 때는 실제로 대조한 범위만 쓴다.
- 이 연재: 기술 선택 글 안의 비교표 절

## 8. 프로젝트 회고

- 독자의 질문: 어떤 경험이었고 무엇을 배웠는가?
- 전개: 배경 → 과정과 주요 판단 → 잘된 점과 아쉬운 점 → 배운 것과 다음 계획
- 필수 요소: 판단의 맥락, 아쉬운 점, 바꿀 것
- 주의: 시간순 나열로 끝내지 않는다. 성과를 부풀리지 않는다.
- 이 연재: 마무리 편이나 각 부의 정리 절에 사용 가능(미정)

## 연재 개발기와 유형의 결합

연재 개발기는 큰 틀이고 각 편은 아래처럼 주도 유형을 갖는다. 아래 배정은 제안이며 작성하면서 조정한다.

| 큰 틀의 단계 | 편 | 주도 유형 | 부분 유형 |
| --- | --- | --- | --- |
| 개발 배경 | 1 | 프로젝트 배경 소개 | 설계(범위 정하기) |
| 기술 선택 | 02-1 | 기술 선택 | 개념 설명, 도구 비교 |
| 기술 선택 | 02-2 | 설계(구성 소개) | 도구 비교 |
| 기술 선택 | 02-3 | 설계(트레이드오프와 한계) | 트러블슈팅 사례 |
| 기술 선택 | 3, 4 | 기술 선택 | 도구 비교 |
| 기능 개발 | 5, 10, 18, 26, 29, 34, 45, 50, 56 | 설계 | 트러블슈팅 사례, 개념 설명 연결 |
| 성능과 검증 | 64 | 성능 실험 | 회고 |
| 성능과 검증 | 68 | 설계(테스트 구성) | 성능 실험 |
| 운영 | 72 | 설계(배포 구조) | 튜토리얼 |
| 이론 | 이론 글 전체 | 개념 설명 | 성능 실험 |

### 결합 규칙

1. 개발 글은 `writing-guide.md`의 개발 글 전개(서비스가 필요한 이유 → 요구사항·환경 제약 → 구조·대안 비교 → 구현 흐름 → 검증 결과 → 남은 문제)를 큰 틀로 하고, 각 절의 서술은 해당 유형의 양식을 따른다.
2. 개발 글 안에서 개념의 깊은 설명이 필요하면 짧게 요약하고 이론 글로 연결한다.
3. 같은 배경 설명을 편마다 반복하지 않고, 도입에서 앞 글을 한두 문장으로만 연결한다.
4. 편에 따라 유형을 억지로 맞추지 않는다. 규격을 따라야 하는 주제(2의 보수, 엔디언 등)는 대안 비교 대신 해석의 정확성과 오류 조건을 중심으로 쓴다.
