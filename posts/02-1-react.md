# 02-1. 프론트엔드를 React로 선택한 이유

앞선 글에서는 비행 시험 데이터 플랫폼을 직접 개발하게 된 배경과 개발 범위를 설명했다. 이번 글에서는 React의 기본 개념과 프론트엔드 도구를 선택하는 기준을 살펴보고, 현재 플랫폼에 React를 적용한 이유를 정리하려 한다.

반복적인 데이터 조회와 추출, 외부 분석 도구와의 연계에는 API를 주로 사용할 것으로 예상한다. 하지만 필요한 데이터를 간혹 내려받거나, 파라미터 정보를 확인하기 위해 매번 API 호출 코드를 작성하는 것은 번거롭다. 사업과 모듈별로 파라미터 DB를 확인하고 수정하거나, 파일을 등록한 뒤 데이터 처리 진행 상황을 확인할 수 있는 화면도 필요하다. 처리된 데이터를 그래프로 확인하고 다운로드하는 기능도 제공하고 있다.

그래서 API로 기능을 제공하면서, 사용자와 관리자가 웹에서도 필요한 업무를 수행할 수 있도록 구성했다. 프론트엔드는 사용자 조작과 화면 표시를 담당하고, FastAPI로 구현한 API 서버에 조회·저장·처리 등의 작업을 요청한다.

웹 UI를 구현하는 방법은 여러 가지다. HTML과 JavaScript로 직접 만들 수도 있고, React나 Vue 같은 도구를 사용할 수도 있다. 각 도구를 비교하기 전에 React가 어떤 방식으로 화면을 구성하는지부터 살펴보려 한다.

## React의 핵심 개념

React는 사용자 인터페이스를 만들기 위한 JavaScript 라이브러리다. 새로운 프로그래밍 언어가 아니라, JavaScript를 사용해 화면을 구성하는 도구다.

React를 이해할 때는 컴포넌트, 선언형 UI, 상태와 props, 단방향 데이터 흐름을 먼저 알아둘 필요가 있다.

**컴포넌트는 화면을 구성하는 단위다.**

버튼이나 입력창처럼 작은 요소도, 검색창과 목록을 포함한 큰 영역도 컴포넌트가 될 수 있다. 작은 컴포넌트를 조합해 전체 화면을 만들고, 각 컴포넌트가 담당하는 기능을 구분한다.

컴포넌트는 화면에서 차지하는 크기보다 기능과 책임을 기준으로 나눈다. 예를 들어 상품 검색 화면은 검색창, 상품 목록, 개별 상품으로 구분할 수 있다. 같은 형태의 상품 표시는 재사용하고, 검색창을 수정할 때는 해당 컴포넌트를 중심으로 코드를 살펴볼 수 있다.

화면 너비에 따라 배치가 달라지는 반응형 디자인과는 구분해야 한다. 하나의 컴포넌트를 유지하면서 CSS로 배치만 변경할 수도 있다.

**선언형 UI는 상태에 따라 화면이 어떤 모습이어야 하는지 작성하는 방식이다.**

JavaScript로 DOM(Document Object Model)을 직접 조작한다면 “버튼을 찾고, 비활성화하고, 문구를 변경한다”와 같은 절차를 작성한다. DOM은 문서를 객체와 트리 구조로 표현한 것으로, JavaScript를 통해 내용을 조회하거나 변경할 수 있다.

React에서는 “저장 중이면 버튼을 비활성화하고 ‘저장 중’이라는 문구를 표시한다”는 관계를 작성한다. 상태가 변경되면 React가 이를 반영해 화면을 갱신한다. 개별 화면 요소를 변경하는 절차보다 상태와 화면의 관계를 중심으로 코드를 작성하는 것이다.

**상태와 props는 역할이 다르다.**

상태(state)는 컴포넌트가 기억하고 변경해야 하는 값이다. 입력 중인 검색어, 선택한 항목, 저장 진행 여부 등이 해당한다.

props는 부모 컴포넌트가 자식 컴포넌트에 전달하는 정보다. 목록에 표시할 데이터뿐 아니라 사용자 조작에 대응할 함수도 전달할 수 있다. 상태는 정보를 관리하는 개념이고, props는 컴포넌트 사이에 정보를 전달하는 수단이다.

**단방향 데이터 흐름은 데이터를 전달하는 방향과 변경하는 위치를 구분하는 방식이다.**

부모가 선택 정보를 관리하고 자식에게 props로 전달하면 자식은 해당 정보를 표시한다. 자식에서 선택을 변경해야 한다면 부모가 전달한 함수를 호출해 변경을 요청한다. 자식이 전달받은 props를 직접 수정하는 방식은 아니다.

이러한 구조는 어떤 값이 어디에서 관리되고 변경되는지 추적하는 데 도움이 된다. 구체적인 코드와 양방향 바인딩과의 차이는 이후 학습 글에서 다룰 예정이다.

이 개념들이 모두 React만의 고유한 특징은 아니다. Vue, Angular, Svelte도 컴포넌트와 상태 변화에 따른 화면 구성을 각자의 방식으로 제공한다. 따라서 개념의 유무뿐 아니라 작성 방식과 필요한 도구의 구성도 비교해야 한다.

## 프론트엔드 도구를 선택하는 기준

대부분의 프론트엔드 도구로 검색, 목록, 입력 폼과 같은 기능을 구현할 수 있다. 기능을 만들 수 있는지와 함께 다음 기준을 살펴볼 필요가 있다.

| 기준 | 확인할 내용 |
| --- | --- |
| 화면의 성격 | 단순한 조회 중심인지, 선택·검색·수정이 연결되는지 |
| 개발자의 경험 | 사용해 본 도구가 있는지, 필요한 개념을 익히는 데 얼마나 걸리는지 |
| 필요한 라이브러리 | 표·차트·트리·입력 기능 등에 필요한 구성을 확보할 수 있는지 |
| 제공하는 범위 | 어떤 기능을 기본 제공하고, 무엇을 별도로 구성해야 하는지 |
| 유지보수 | 문서·업데이트·의존성과 담당자 변경에 어떻게 대응할지 |
| 배포 환경 | 빌드와 설치 절차가 운영 환경의 제약에 맞는지 |

React는 UI 라이브러리이므로 애플리케이션에 필요한 모든 기능을 기본 제공하지는 않는다. 화면 전환이나 서버 데이터 관리 등은 필요에 따라 다른 도구와 조합한다.

반면 프레임워크는 애플리케이션을 만드는 기본 구조와 실행 흐름을 제공하고, 개발자는 그 안에 필요한 기능을 작성한다. Angular는 컴포넌트뿐 아니라 라우팅과 폼 등의 기능도 제공하는 프론트엔드 프레임워크다.

라우팅은 URL에 따라 어떤 화면을 보여줄지 연결하는 기능이다. 폼은 사용자에게 정보를 입력받고 확인한 뒤 제출하는 기능으로, 입력값 검증과 오류 표시도 함께 다룬다.

도구가 제공하는 범위가 넓으면 공통된 구조로 개발할 수 있고, 별도로 조합하는 방식에서는 필요한 구성을 직접 선택할 수 있다. 어느 쪽이 적합한지는 필요한 기능과 개발·유지보수 방식에 따라 달라진다.

## 도구별 비교

아래 표는 공식 문서에서 설명하는 주요 특징과 선택할 때 확인할 항목을 정리한 것이다. 같은 화면을 각각 구현해 성능이나 개발 시간을 측정한 결과는 아니다.

| 방식 | 주요 특징 | 선택할 때 확인할 부분 |
| --- | --- | --- |
| HTML과 JavaScript로 직접 구현 | DOM 조작과 이벤트 처리를 직접 작성 | 상태와 화면 갱신 로직을 직접 관리할 범위 |
| React | 컴포넌트와 상태를 중심으로 UI 작성 | 데이터 흐름과 상태 설계, 함께 사용할 도구 |
| Vue | 템플릿과 반응성 기반으로 UI 작성 | 템플릿 문법과 반응성 규칙, 공식 도구의 활용 |
| Angular | 컴포넌트·라우팅·폼·의존성 주입 등 제공 | 제공하는 구조와 기능이 개발 방식에 맞는지 |
| Svelte | 컴포넌트를 컴파일해 실행할 JavaScript 생성 | 작성 방식과 필요한 라이브러리의 적용 가능성 |

HTML과 JavaScript를 직접 작성하는 간단한 구성은 별도의 빌드 과정 없이 실행할 수 있다. 기능이 적다면 필요한 동작을 직접 연결하는 방식으로도 충분할 수 있다. 다만 검색과 선택, 수정 기능이 연결되면 상태 변경에 따라 갱신해야 하는 화면 요소도 많아진다.

React 같은 도구는 이러한 관계를 컴포넌트와 상태로 표현하도록 돕는다. 대신 해당 도구의 작성 방식을 익히고 프로젝트 구성도 관리해야 한다.

React를 사용하면 항상 더 빠르거나 코드가 짧아지는 것은 아니다. Vue가 항상 더 쉽거나 Angular는 큰 프로젝트에만 적합하다고 단정할 수도 없다. 필요한 기능과 기존 경험, 관리해야 하는 코드의 범위를 함께 봐야 한다.

## 이 플랫폼에 React를 적용한 이유

이 플랫폼의 파라미터 관리 화면은 선택과 검색, 수정, 저장이 서로 연결되어 있다.

사업을 선택하면 모듈 목록을 보여주고, 모듈을 열면 파라미터 목록을 표시해야 한다. 여러 항목을 선택해 작업하거나 기존 정보를 입력 폼으로 가져와 수정하는 기능도 필요하다. 하나의 조작으로 화면 내 여러 영역이 함께 변경되는 구조다.

이러한 화면에서는 **상태를 기준으로 표시 내용을 결정하고, 기능별로 코드를 나눠 관리하는 방식**이 적합하다. 현재 React 구현도 이 방식으로 구성하고 있다.

파라미터 관리 화면은 탐색 트리, 모듈 목록, 파라미터 목록, 입력 폼으로 나눴다. 입력 항목을 변경할 때와 목록의 표시 방식을 변경할 때 살펴볼 코드를 구분할 수 있도록 했다.

여러 영역에서 함께 사용하는 선택 정보는 상위 컴포넌트에서 관리하고 필요한 곳에 전달한다. 반면 상세 정보를 보는 대상과 일괄 작업의 대상처럼 용도가 다른 정보는 구분한다.

컴포넌트 사이에 전달할 정보가 많기 때문에 React를 사용해야 하는 것은 아니다. 중요한 것은 정보를 어디에서 관리하고, 각 영역에 어떻게 전달하며, 변경을 어디에서 처리할지 구분하는 것이다. React는 이를 컴포넌트와 상태, props를 통해 표현할 수 있다.

이 요구사항은 다른 도구로도 구현할 수 있다. 현재 화면의 성격은 React가 적합한 이유이지만, Vue나 Svelte보다 우수하다는 근거는 아니다. 이 글에서는 현재 구현을 기준으로 React의 특징이 필요한 기능에 어떻게 연결되는지 정리했다.

현재 프론트엔드는 React만으로 구성되어 있지는 않다. 화면 전환과 그래프, 스타일, 개발과 빌드에는 별도의 도구를 함께 사용하고 있다.

다음 글에서는 Vite, React Router, Recharts, Tailwind CSS 등이 각각 어떤 역할을 담당하고, React와 어떻게 연결되는지 살펴보려 한다.
