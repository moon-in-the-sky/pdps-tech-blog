# 01. 비행 시험 데이터 플랫폼을 직접 개발하게 된 이유

비행 시험이 끝나면 레코더에 저장된 데이터를 엔지니어가 분석에 활용할 수 있는 형태로 변환하여 배포하는 작업이 시작된다.

나는 비행 시험 계측 업무에서 데이터 처리와 파라미터 DB 관리, 데이터 배포 업무를 맡고 있고, 현재 **비행 시험 데이터를 처리하고 배포하는 플랫폼**을 개발하고 있다.

이번 글에서는 세부 구현에 대한 내용을 설명하기에 앞서, 어떤 업무를 다루는 플랫폼이며 왜 하나의 시스템으로 구성하려 했는지 정리한다.

비행 시험 데이터 파일에는 서로 다른 통신 프로토콜의 데이터가 들어 있다. 이를 처리하고 배포하려면 파일의 구조뿐 아니라 각 데이터의 처리 프로세스도 알아야 한다.

예를 들어 어떤 값을 추출하려면 해당 신호가 어느 채널에 있고, 패킷의 어느 위치에서 시작하며, 몇 비트를 어떤 자료형(int, float 등)으로 읽어야 하는지 알아야 한다. 추출한 값에 단위 변환이 필요한 경우도 있다. 여러 데이터를 함께 비교하려면 각 샘플의 시간도 올바르게 처리해야 한다.

이처럼 데이터를 왜곡 없이 처리하기 위해서는 데이터 내 각 파라미터의 위치, 자료형, 변환 규칙에 대한 정확한 정보가 필요하다. 이 플랫폼에서는 해당 정보를 파라미터 DB로 관리한다. 따라서 데이터 처리 결과의 정확성은 처리 로직과 파라미터 DB 양쪽에 달려 있다. 코드가 정상적으로 실행되더라도 처리 대상과 맞지 않거나 잘못된 파라미터 정보를 적용하면 결과가 달라질 수 있다.

비행 시험 업무에서는 계측 파라미터의 변경 사항을 DB에 반영하고, 신규 모듈이 추가되면 해당 모듈과 파라미터 정보를 등록해야 한다. 데이터 처리 시에는 처리 대상에 맞는 파라미터 DB를 적용해야 하므로, DB 관리와 데이터 처리는 서로 연결된 업무다.

현 시스템은 신규 모듈 추가에 대한 대응이 어렵고, AI를 활용한 데이터 분석 또는 API 기능 제공 등 기술 발전의 부산물을 추가할 수 없는 구조이다. 그렇기에 비행 시험 데이터 플랫폼 자체 개발을 진행하게 되었다. 플랫폼의 개발 범위에 파라미터 DB 관리 기능도 포함했다. 사업별 모듈과 파라미터 정보를 등록·수정하고, 관리한 정보를 실제 데이터 처리에 적용할 수 있도록 구성하고자 했다.

데이터 처리가 끝나면 처리된 데이터를 엔지니어에게 배포해야 한다. 엔지니어는 분석에 필요한 파라미터와 시간 구간을 선택하고, 사용하는 분석 도구에서 읽을 수 있는 형식으로 데이터를 받아야 한다. 여러 파라미터를 개별 파일로 내려받거나, 하나의 시간 축에 맞춰 함께 출력해야 하는 경우도 있다.

이러한 사용 방식을 지원하기 위해 처리 결과의 저장과 데이터 추출·다운로드 기능도 개발 범위에 포함했다. 저장할 때는 이후 필요한 데이터를 효율적으로 읽을 수 있어야 하고, 다운로드할 때는 사용자가 선택한 조건과 형식에 맞게 제공해야 한다.

따라서 플랫폼은 데이터 **파라미터 DB 관리부터 데이터 처리, 결과 저장, 추출과 배포까지 이어지는 업무**를 하나의 시스템에서 수행할 수 있도록 구성하고 있다.

| 단계 | 제공하는 기능 | 필요한 이유 |
| --- | --- | --- |
| 파라미터 DB 관리 | 사업·모듈·파라미터 등록과 수정 | 데이터 처리에 필요한 정보를 관리하고 처리에 적용하기 위해 |
| 원시 파일 등록과 처리 | 기록 파일에서 파라미터 추출 | 기록된 데이터를 분석에 사용할 수 있는 값으로 변환하기 위해 |
| 작업 상태 확인 | 대기·진행·완료·실패 상태 확인 | 작업 진행 상황을 확인하고 실패 시 후속 조치를 하기 위해 |
| 변환과 계산 | 단위 변환과 계산 파라미터 처리 | Raw 값과 여러 입력 데이터를 분석에 필요한 값으로 변환하기 위해 |
| 결과 추출과 배포 | 필요한 데이터 선택과 파일 다운로드 | 엔지니어가 분석 목적에 맞는 데이터를 사용할 수 있도록 제공하기 위해 |

플랫폼을 개발하면서 우선적으로 고려하는 것은 데이터 정확성이다. 값뿐 아니라 시간, 샘플 수, 누락 구간도 처리 결과에 영향을 준다. 데이터가 없는 구간을 임의로 0으로 채우거나, 시간 정보가 비정상적으로 보인다는 이유만으로 데이터를 제거하면 원래 기록과 다른 결과를 만들 수 있다. 따라서 원시 데이터를 보존하면서, 변환과 시간 정렬이 필요한 경우에는 적용 기준을 명확하게 정해야 한다.

처리와 다운로드 성능도 고려해야 한다. 대용량 데이터를 처리하는 시간을 줄이되, 기존 시스템의 값과 시간이 신규 시스템과 동일한지 확인해야 한다. 여러 사용자가 동시에 접근하는 상황에서는 개별 작업의 속도와 함께 로그인, 조회, 다운로드 등 다른 기능이 정상적으로 동작하는지도 검증해야 한다.

실행 환경은 폐쇄망의 Windows 서버다. 외부 인터넷에 연결할 수 없는 환경에서 설치하고 운영해야 하므로 의존성 준비와 배포 절차도 개발 과정에 포함된다. 또한 데이터 처리와 사용자 요청이 서버 자원을 함께 사용하기 때문에 작업별 CPU·메모리·디스크 사용량과 동시 실행 범위를 고려해야 한다.

현재 플랫폼은 개발과 검증을 진행하고 있다. 이 연재에서는 각 서비스를 제공하는 이유와 함께, 이를 구현하기 위해 어떤 구조와 기술을 선택했는지 설명할 예정이다. 파라미터 DB 설계, 바이너리 데이터 처리, 저장 구조, 병렬 처리, 다운로드 성능 개선과 테스트 과정도 순서대로 다룬다. 성능이 개선된 사례뿐 아니라 기대한 효과를 얻지 못한 시도와 남은 문제도 함께 기록하려 한다.
